# قائمة تحقق وخطة انتقال Worker إلى Staging

**الحالة: وثيقة تخطيط للمراجعة فقط.** لم تُنشأ موارد Cloudflare، ولم يُعدّل إعداد سحابي، ولم يُنفذ نشر أو migration بعيد أو اختبار GitHub E2E حقيقي. الأوامر أدناه أمثلة لتنفيذ مستقبلي بعد اعتماد بوابة كل مرحلة؛ لا تنفذها الآن.

## حدود التكامل وما نريد إثباته

- `POST /run` في Worker يستدعي حاليًا `createLocalSmokeRunner`؛ **لا يشغّل GitHub plugin** ولا يستخدم GitHub token. نجاح `/run` المنشور يثبت مسار smoke/persistence فقط.
- اختبار GitHub E2E الحقيقي منفصل، عبر CLI، وينشئ فرعًا وcommit وPull Request حقيقيًا. يجب تشغيله على مستودع اختبار مخصص بعد موافقة مستقلة.
- حدود D1 المنفذة لكل Access subject: 10 تشغيلات/دقيقة، 100 تشغيل/يوم، و120 قراءة/دقيقة. هذه لا تغني عن حماية Cloudflare edge، ولا نعتبر حدود edge مفعلة حتى تُضبط وتُختبر في الحساب.
- لا نعتبر Staging اعتمادًا للإنتاج؛ يلزم قرار ومراجعة منفصلان قبل أي ترحيل/نشر Production.

## الوضع الحالي المعروف

- إعداد Wrangler الأساسي يستخدم `celia-runs` و`CELIA_MODE = "local"`؛ لا يوجد إعداد `env.staging` جاهز في `apps/worker/wrangler.toml`.
- migrations `0001` و`0002` و`0003` طُبقت واختُبرت محليًا فقط. لا توجد نتيجة موثقة عن قاعدة Cloudflare بعيدة.
- مصادقة Access والحدود الجديدة لها اختبارات محلية؛ لم يُختبر Worker على Cloudflare runtime أو خلف Access حي.
- اختبار GitHub E2E الحقيقي متخطّى في الاختبارات الافتراضية ولم يُشغّل.

## بوابات القرار (لا تجاوز تلقائي)

| البوابة | يلزم قبل الانتقال | القرار |
|---|---|---|
| G0 — النطاق | مالك مسؤول، hostnames، مستخدمو Staging، مدة التجربة، وسقف التكلفة/الطلبات | موافقة صريحة |
| G1 — العزل | حساب/موارد Staging منفصلة عن Production، D1 جديدة، ومسار لا يتجاوز Access | مراجعة إعدادات فقط |
| G2 — الهوية والحماية | تطبيق Access وaudience صحيحان، CORS مضبوط، edge rate rules متاحة ومختبرة | موافقة أمنية |
| G3 — البيانات | تأكيد اسم/ID قاعدة Staging، حالة فارغة أو خطة بيانات معتمدة، وخطة استعادة | موافقة قبل remote migration |
| G4 — النشر | dry-run صحيح، migration state متوقعة، خطة rollback واختبارات جاهزة | موافقة مستقلة قبل كل نشر |
| G5 — GitHub E2E | مستودع اختبار حصري، token محدود، ملفات/فروع/PRs مسموحة وخطة تنظيف | موافقة مستقلة قبل تشغيل الاختبار الحقيقي |

إذا فشلت أي بوابة أو تعذر إثبات قيمة إعداد، **توقف** ولا تستخدم موردًا إنتاجيًا كبديل.

## المرحلة 0 — حسم التصميم قبل إنشاء الموارد

- [ ] تعيين مالك تقني ومراجع أمني، ومَن يوافق على كل بوابة.
- [ ] اختيار اسم Worker وhostname ثابتين لـStaging API، وhostname ثابت للـConsole. تجنب Preview hostname متغيرًا إذا كان لا يمكن إدراجه كـCORS origin ثابت.
- [ ] تحديد حساب Cloudflare المقصود ووسيلة التحقق من account ID، دون تسجيل بيانات اعتماد في Git أو المحادثة.
- [ ] الاتفاق على أن قاعدة Staging D1 **جديدة ومستقلة**، وعدم إعادة استخدام database ID أو بيانات Production.
- [ ] تحديد سياسة حفظ/حذف سجل التشغيل وعدادات `request_limits`، وفترة الاحتفاظ بآثار الاختبارات.
- [ ] مراجعة تكلفة/حصة Workers وD1 وCloudflare Access وقواعد edge المتاحة في الخطة؛ لا تفترض أن ميزة rate limiting بعينها متاحة قبل التحقق من الحساب.

**مخرج المرحلة:** مخطط موارد وقيم أسماء/hostnames معتمدة، بلا أسرار؛ لا موارد منشأة بعد.

## المرحلة 1 — إعداد الموارد المعزولة (بعد G0 فقط)

- [ ] إنشاء D1 منفصلة باسم Staging، وتسجيل الاسم وdatabase ID في سجل نشر داخلي محمي؛ لا تضع بيانات اعتماد في المستودع.
- [ ] إضافة إعداد `[env.staging]` مستقل في `apps/worker/wrangler.toml`، مع Worker name مميز، وD1 binding `DB` مربوطًا بـStaging database ID، و`migrations_dir = "migrations"`.
- [ ] تعريف قيم Staging صراحةً داخل البيئة، وعدم الاتكال على توريث غامض من الإعداد العام: `CELIA_MODE` و`ACCESS_TEAM_DOMAIN` و`ACCESS_AUD` و`CONSOLE_ORIGIN`.
- [ ] ضبط إعداد Worker بحيث لا يوجد `workers.dev` أو hostname بديل عام يتجاوز حماية Access؛ إذا تعذر إغلاق bypass، لا تنشر.
- [ ] بناء Console preview مستقل مع `VITE_API_BASE_URL` يشير حصريًا إلى Staging API. لا توجه Console Staging إلى API أو D1 إنتاج.
- [ ] التأكد من أن `CONSOLE_ORIGIN` هو origin كامل واحد مطابق تمامًا (scheme + host، دون path) وأن إعداد CORS يسمح بالـConsole المقصود فقط.
- [ ] تشغيل dry-run ومراجعة الاسم والـbindings والـvars قبل أي أمر remote:
  ```bash
  cd apps/worker
  pnpm exec wrangler deploy --env staging --dry-run
  ```

**شرط القبول:** ناتج dry-run يعرض موارد Staging الصحيحة فقط، ولا يحتوي اسم/ID إنتاج. الـdry-run ليس نشرًا ولا يثبت حماية الخدمة الحية.

## المرحلة 2 — Cloudflare Access والأسرار وحماية edge (بعد G1)

### Cloudflare Access

- [ ] إنشاء Access application للـAPI hostname، وسياسة سماح لمجموعة/مستخدمين محددين فقط؛ لا تستخدم سياسة عامة.
- [ ] حماية Console preview أيضًا بما يتوافق مع تدفق تسجيل الدخول، مع اختبار أن متصفح المستخدم المسموح يستطيع إرسال طلب credentialed إلى API.
- [ ] تثبيت Access team domain و`ACCESS_AUD` الخاص بالتطبيق الصحيح في Worker Staging، ومطابقة issuer/audience مع إعداد التطبيق.
- [ ] التحقق من أن Access policy تطبق على hostname والمسارات المقصودة وأن Worker يتحقق تشفيريًا من `Cf-Access-Jwt-Assertion` (issuer/audience/signature/expiry/subject). إغلاق hostname أو route بديل يمنع تجاوز سياسة الدخول على الحافة؛ لا تستبدل تحقق Worker بمجرد وجود رأس.
- [ ] اختبار غياب الرمز، رمز من audience مختلفة، رمز منتهي/غير صالح، وهوية مسموحة. المتوقع: رفض آمن (عادةً `401`)، و`503` عند غياب إعداد Worker اللازم.

### الأسرار

- [ ] لا حاجة إلى GitHub token لمسار Worker smoke الحالي؛ لا تضفه إلى Worker أو Console.
- [ ] ضع أي secret مطلوب مستقبلًا في مخزن Cloudflare/CI المخصص، لا في `[vars]` أو ملفات committed أو build output.
- [ ] لا تشارك مفاتيح، tokens، JWTs، cookies، أو headers مصادقة في logs أو tickets أو المحادثة.

### حماية المعدل على Cloudflare edge

- [ ] أضف قاعدة coarse-grained للـAPI hostname، مع تمييز `POST /run` عن مسارات القراءة، باستخدام أسلوب إجراء لا يتطلب challenge تفاعليًا لطلبات API.
- [ ] اجعل الحد edge مكملًا لحد D1 per-subject، لا بديلًا عنه. حدد المفتاح والحد والفترة بعد مراجعة الخطة/المزايا المتاحة؛ لا تنسخ أرقامًا افتراضية دون قرار.
- [ ] اختبر القاعدة على Staging، وتأكد من أن الاستجابة لا تكشف تفاصيل ولا تمنع مستخدمي الاختبار الطبيعيين. دوّن آلية رفع الحظر/الاستثناء المؤقت.
- [ ] راقب رفض edge منفصلًا عن `429` الصادر من Worker، لتحديد الطبقة التي فرضت الحد.

## المرحلة 3 — مراجعة البيانات وتطبيق migrations (بعد G3 فقط)

- [ ] تحقق من account ID واسم/ID D1 المقصودين باستخدام قائمة الموارد في الحساب، وقارنها بالقيم في `[env.staging.d1_databases]`.
- [ ] أكد أن قاعدة Staging جديدة/فارغة. Migration `0002_run_ownership.sql` يترك السجلات القديمة `owner_id = NULL`؛ هذه السجلات لا تظهر للمستخدمين، لذا لا تُرحّل بيانات قديمة دون مراجعتها وخطة صريحة.
- [ ] إن وجدت بيانات، خذ export/backup مناسبًا وتحقق من إمكانية استعادته قبل التغيير؛ إذا تعذر ذلك فتوقف.
- [ ] اعرض حالة migrations الحالية على قاعدة Staging، وتأكد أن الهدف ليس Production وأن التسلسل المتوقع هو `0001_runs.sql` ثم `0002_run_ownership.sql` ثم `0003_request_limits.sql`.
- [ ] بعد موافقة G3، طبّق migrations على اسم D1 المطابق تمامًا لـ`database_name` في env staging. مثال إذا كان الاسم `celia-runs-staging`:
  ```bash
  cd apps/worker
  pnpm exec wrangler d1 migrations apply celia-runs-staging --env staging --remote
  ```
- [ ] تحقق من أن سجل migrations والجداول/الفهارس موجودة في Staging فقط، وأن جدول `request_limits` قابل للقراءة والكتابة.
- [ ] لا تعدّل migration مطبقة ولا تحاول rollback يدويًا. هذه migrations إضافية؛ الرجوع البرمجي لا يعني حذف أعمدة/جداول أو استرجاع DB تلقائيًا.

**شرط القبول:** سجل migrations مطابق للنسخة المنشورة، وDB ID مؤكد أنه Staging. لا تنتقل للنشر عند أي اختلاف.

## المرحلة 4 — النشر والتحقق الوظيفي (بعد G4 فقط)

النشر، تطبيق migration، ونشر Console ثلاث تغييرات منفصلة؛ يلزم موافقة واضحة قبل كل تغيير. بعد مراجعة dry-run وخطة rollback:

1. نشر Worker إلى بيئة Staging فقط.
2. نشر Console preview بإعداد API Staging فقط.
3. التأكد من عدم وجود route بديل غير محمي، ومراجعة Access/WAF logs دون أسرار.

### مصفوفة اختبارات Staging

- [ ] `/health` يعمل وفق التصميم ولا يعرض معلومات حساسة.
- [ ] طلب مجهول لكل مسار خاص (`/tasks`, `/runs`, `/runs/:id`, `/run`) مرفوض؛ رمز مزور/منتهي/بـaudience خاطئ مرفوض.
- [ ] مستخدم Access A ينشئ تشغيلًا smoke تجريبيًا، ويظهر السجل مربوطًا بـ`sub` الخاص به؛ مستخدم B لا يستطيع قراءة أو تعداد سجل A، والعكس.
- [ ] Console origin المعتمد ينجح مع credentials، والـorigin غير المسموح لا يحصل على سماح CORS له. استجابة API تحمل `Cache-Control: private, no-store` و`Vary: Origin` عند الاقتضاء.
- [ ] أرسل body أكبر من 64 KiB بطلب Staging آمن وتحقق من رفضه برسالة تحقق ثابتة؛ راقب أن الوسيط/edge قد يرفض الطلب قبل Worker. اختبار تطابق الرأس غير الموثوق يغطيه الاختبار المحلي، إذ قد يعيد Cloudflare تطبيع النقل.
- [ ] تحقق من `429` و`Retry-After` من Worker في اختبار محدود بهوية Staging مخصصة؛ لا تستهلك حصة مستخدم حقيقي. إثبات حد اليوم (101 محاولة) اختبار load غير افتراضي، ولا ينفذ إلا بموافقة منفصلة وخطة لتجنب التكلفة/الضجيج.
- [ ] اختبر أخطاء D1/runner غير المتوقعة محليًا عبر الاختبارات القائمة: الرد العام `request failed` مع `request_id`، بلا نص exception. لا تعطل قاعدة Staging عمدًا لمجرد التحقق؛ أي حقن فشل حي يحتاج موافقة وخطة استعادة.
- [ ] راجع سجلات Cloudflare بحثًا عن secrets أو JWT أو task payloads حساسة؛ تحقق من correlation باستخدام `request_id` دون طباعة بيانات حساسة.
- [ ] سجل النتائج والوقت والـWorker version وmigration versions؛ لا ترفق رموز مصادقة أو cookies.

### قرار rollback/إيقاف

- أوقف اختبار المستخدمين عند فشل المصادقة، خلط قاعدة Staging/Production، كشف خطأ داخلي، أو اختلاف CORS/Access غير مفهوم.
- يمكن إرجاع Worker إلى نسخة Staging سابقة متوافقة، مع إبقاء migrations الإضافية. **لا** تُسقط migration أو تحذف البيانات تلقائيًا.
- لا تنفذ restore أو حذف موارد دون موافقة صريحة وتحقق من النسخة/الوجهة.
- احتفظ بسجل قرار ومَن وافق ووقت الإيقاف/الاستئناف.

## المرحلة 5 — GitHub E2E الحقيقي (بوابة منفصلة G5)

- [ ] أنشئ/اختر مستودع اختبار مخصصًا منفصلًا عن مستودعات الإنتاج، وراجع قواعد الحماية وسياسة PRs والتنظيف.
- [ ] استخدم GitHub token محدودًا لهذا المستودع وبالصلاحيات الدنيا اللازمة للقراءة/كتابة الملفات وإنشاء Pull Requests؛ ضعه في secret store محمي مؤقتًا.
- [x] حاجز CLI واختباراته يرفضان غياب `CELIA_E2E_OWNER` و`CELIA_E2E_REPO`؛ حُذفت defaults من workflow وأضيف تحقق يطابق الهدف تمامًا مع `CELIA_E2E_ALLOWED_REPOSITORY`.
- [ ] إعداد GitHub Environment باسم `github-e2e` مع required reviewers وتقييد deployment إلى `main`؛ ضع `CELIA_E2E_ALLOWED_REPOSITORY` و`E2E_GH_TOKEN` كـenvironment secrets لمستودع اختبار مخصص (ليس repository secrets)، ثم شغّل E2E الحقيقي بموافقة صريحة. لم تُنفذ إعدادات GitHub الحية أو التشغيل.
- [ ] لا تشغل الاختبار إلا بموافقة صريحة لأن نتيجته أثر حقيقي: فرع، commit، ملف، وPull Request. اضبط `CELIA_E2E_REAL=1` و`GH_TOKEN` (أو `GITHUB_TOKEN`) في بيئة التشغيل المحمية و`CELIA_E2E_REPORT_DIR` إلى مسار artifacts غير ملتزم بـGit.
- [ ] نفّذ الاختبار منفصلًا عن نشر Worker؛ النتيجة تثبت CLI GitHub adapter فقط، ولا تثبت أن Worker `/run` ينفذ GitHub.
- [ ] تحقق من verdict، وchain validity، والـPR والـcommit والأدلة، ثم أغلق/احذف موارد الاختبار وفق سياسة المستودع وموافقة المالك. لا تحفظ token أو بيانات خاصة في التقرير.

## معايير الخروج من Staging

- [ ] كل بوابات G0–G5 المطلوبة موثقة وموقعة من أصحابها.
- [ ] لا توجد موارد أو IDs مشتركة مع Production، ولا طريق غير محمي إلى Worker.
- [ ] اختبارات الهوية والعزل والحجم والـrate limit/CORS اجتازت أو سُجلت استثناءات معتمدة.
- [ ] نتائج GitHub E2E الحقيقية، إن نُفذت، موثقة على مستودع اختبار وبشكل منفصل عن Worker smoke.
- [ ] خطة حذف/احتفاظ موارد Staging وتقرير المخاطر المتبقية معتمدان.

**لا تعني إكمال هذه القائمة تلقائيًا الموافقة على Production.** يتطلب الانتقال إلى Production قرارًا جديدًا ومراجعة موارد/مفاتيح/بيانات وإجراءات نشر مستقلة.
