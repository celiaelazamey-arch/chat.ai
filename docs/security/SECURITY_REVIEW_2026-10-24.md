# مراجعة حدود الأمان — 2026-10-24

## النطاق والمنهج

مراجعة ساكنة موجّهة لمسار Cloudflare Worker وD1، ومسارات الأسرار المشار إليها في الشيفرة. لم تُجرَ اختبارات اختراق أو طلبات إلى الخدمة الحية؛ لا تُعد هذه المراجعة شهادة أمنية.

## النتائج ذات الأولوية

### P0 — المصادقة والتفويض (الملاحظة الأصلية ومعالجة محلية)

- **النتيجة الأصلية:** مسارات `GET /runs`, `GET /runs/:id`, `GET /tasks`, و`POST /run` لم تكن تتحقق من الهوية، وكانت البيانات مشتركة على مستوى القاعدة.
- **المعالجة الحالية في الفرع:** أضيف تحقق Cloudflare Access JWT RS256 (issuer/audience/expiry/not-before/subject) في `apps/worker/src/access-auth.ts`. كل مسارات API الخاصة تتطلب assertion صالحًا؛ `GET /health` وCORS preflight مستثنيان. غياب إعدادات Access يرجع `503`، والرمز المفقود/غير الصالح يرجع `401`.
- أضيف `owner_id` في migration `0002_run_ownership.sql`; تُحفظ التشغيلات مع `sub` ويُقيد عرض القوائم والتفاصيل بـ`owner_id`. اختبارات Worker تغطي رفض الهوية وعزل سجل مستخدم عن آخر.
- تُخزّن مفاتيح JWKS مؤقتًا، وتُحد طلبات التحديث بفاصل 30 ثانية لكل نطاق (بما يشمل محاولات التحديث الفاشلة)، مع دمج الطلبات المتزامنة؛ هذا يحد من تحويل `kid` مجهول إلى طلبات متكررة لشهادات Access. يغطيه اختبار مع تعطل endpoint.
- أضيفت `credentials: include` للواجهة، و`Access-Control-Allow-Credentials`, و`Vary: Origin`، و`Cache-Control: private, no-store` لاستجابات API.
- **ما لم يحدث:** لم تُضبط Cloudflare Access أو متغيرات `ACCESS_TEAM_DOMAIN` و`ACCESS_AUD` في بيئة حية، ولم تُشغّل migration على D1 فعلي. لذلك هذا تنفيذ محلي يحتاج إعداد ونشر وتحقق staging، وليس تأكيدًا أن نقطة الخدمة الحية محمية بالفعل.

CORS ليس مصادقة: يمنع بعض قراءات المتصفح العابرة للأصول، لكنه لا يمنع استدعاءات HTTP المباشرة. لذلك يظل التحقق المشفر من Access JWT والتفويض على المالك هما الضابطين الأساسيين.

### P1 — فرض حد فعلي لحجم جسم الطلب (معالجة محلية)

- `apps/worker/src/index.ts` يتحقق الآن من Content-Length إن وُجد، ثم يقرأ stream ويوقفه عند تجاوز 64 KiB حتى إذا غاب الرأس أو لم يطابق الحجم الحقيقي.
- اختبارات Worker تغطي الرأس المعلن والحجم الفعلي لجسم بلا Content-Length. ما يزال يلزم اختبار هذا السلوك على Cloudflare runtime الفعلي قبل الإنتاج.

### P1 — تحديد المعدل والحصة (حماية محلية مع حاجة لضبط edge)

- أضيفت عدادات fixed-window ذرية مشتركة عبر D1 ومفاتيح مقيدة بهوية Access subject: 10 تشغيلات/دقيقة، 100 تشغيل/يوم، و120 قراءة/دقيقة. تجاوز الحد يرجع `429` و`Retry-After`.
- يحد هذا الاستنزاف على مستوى المستخدم الموثق؛ لكن ما زالت حماية المعدل على Cloudflare edge مفيدة لتقليل الضغط قبل وصول الطلبات إلى Worker/D1. وسياسة الاحتفاظ بسجلات المستخدمين وعداداتهم تحتاج تحديدًا تشغيليًا.

### P2 — حجب تفاصيل الاستثناءات الداخلية (معالجة محلية)

- أخطاء D1 والتنفيذ تُعاد الآن برسالة عامة `request failed` ومعرّف طلب، لا بنص الاستثناء الأصلي. أخطاء إدخال العميل المعروفة فقط تُصنّف `400`.
- لا يسجل الكود تفاصيل الاستثناءات الحساسة؛ يلزم ربط معرّف الطلب بمنظومة Observability آمنة ومنقحة عند الإعداد السحابي.

### P2 — فصل Staging/Production وإعداد السرّية غير موضحين في Wrangler

- `apps/worker/wrangler.toml:6-13` يعرّف `CELIA_MODE = "local"` وربط D1 واحدًا، ولا يعرّف أقسام بيئات منفصلة أو D1 مستقلًا لـStaging في الملف الحالي.
- هذا لا يثبت أن الإعداد الحي خطأ؛ لكنه يعني أن فصل البيئات وسرّية إعدادات النشر يحتاجان إثباتًا خارج هذا الملف قبل النشر التجريبي.
- **المعالجة:** إعداد `env.staging` و`env.production` بموارد منفصلة، مراجعة migrations، واستخدام إعدادات/Secrets عبر Cloudflare لا أسرار داخل المستودع.

## ضوابط سليمة ظهرت في المراجعة

- استعلامات D1 تستخدم placeholders (`?`) بدل دمج قيم المستخدم في SQL (`apps/worker/src/storage.ts:25-43,46-80`).
- حجم الصفحة محدود بحد أقصى 100 (`apps/worker/src/storage.ts:19-22`).
- قائمة الأصول المسموح بها لـCORS صريحة في Worker؛ لكن هذا ضابط متصفح وليس بديلًا عن المصادقة.
- `InMemoryVault` موصوف صراحة بأنه dev/test فقط (`adapters/vault/src/vault.ts:12-13`)، وقراءة سر GitHub تمر عبر `VaultAdapter` عند استخدام `resolveToken` (`plugins/tools/github/src/credentials.ts:8-14`). ما زال يلزم إثبات أن كل مسار إنتاج يستخدم Vault فعليًا ولا يمرر اعتمادًا خامًا عبر متغيرات البيئة.

## بوابة الانتقال إلى Staging

1. طبقة التحقق والعزل أضيفت محليًا؛ قبل Staging يجب ضبط Cloudflare Access و`ACCESS_TEAM_DOMAIN` و`ACCESS_AUD`، تطبيق migration `0002` على D1 Staging منفصل، والتحقق من رفض/عزل المستخدمين عبر endpoint المنشور.
2. نُفذ حد stream فعلي واختُبر محليًا؛ أعد التحقق على Cloudflare runtime.
3. نُفذت fixed-window limits في D1؛ أضف/اضبط حماية Cloudflare edge وسياسة الاحتفاظ للعدادات والسجلات.
4. حُجبت رسائل الاستثناءات وأضيف request ID؛ اربطها بمراقبة منقحة عند Staging.
5. أنشئ بيئات Staging/Production منفصلة مع D1 مستقل وSecrets مُدارة.
6. بعد ذلك نفّذ اختبارات أمنية آلية وGitHub E2E حقيقي في Staging باستخدام حساب/مستودع اختبار محدود الصلاحيات.

**الحالة:** أضيفت محليًا مصادقة Access والتفويض على المالك، حد جسم stream فعلي، معدلات/حصص D1، ورسائل خطأ آمنة، وجميعها لها اختبارات. لا يُصرّح ببدء Staging الحساس قبل تهيئة Access وD1 منفصلة وتطبيق migrations والتحقق على المسار الحي. حماية Cloudflare edge، الاحتفاظ التشغيلي، واختبار Cloudflare الفعلي ما تزال مفتوحة.
